# Приёмка и определение готовности

Это план будущих проверок. При подготовке пакета эти сценарии не запускались.
Команды и записи разрешаются только явным запросом конкретного запуска.

После подготовки пользователь разрешил реализацию и изолированные проверки.
Фактические результаты и ограничения приведены в
[05-implementation-report.md](05-implementation-report.md); этот файл сохраняет
исходные критерии, а не заменяет их статусом выполнения.

## 1. Приоритеты

**P0 — блокирует приёмку:** потеря данных, публикация без явного действия,
обход прав, смешение сайтов, потеря перевода/связей, silent overwrite, утечка
контента или заявок, изменение рабочих данных без разрешения.

**P1 — блокирует завершение объёма:** отсутствует обязательный экран/операция,
неработающие сохранение/preview/выбор файлов, недоступная клавиатура,
горизонтальное переполнение основной формы, ошибки без пути восстановления,
несохранение фильтров или ложное состояние успеха.

**P2 — визуальное качество:** неровная типографика, несогласованные отступы,
dropdown с несогласованной темой, обрезанные подписи, слабая иерархия, скачущие строки,
непоследовательные empty/loading states. Значимые повторяющиеся P2 исправляются
до сдачи; не превращать это в бесконечную переделку вкусовых деталей.

## 2. Условия безопасной проверки

- Backend-тесты используют отдельную тестовую БД.
- Браузерные записи — только изолированное окружение с синтетическими данными.
- Существующие реальные материалы, права, пароли и заявки не изменяются.
- Email не отправляется. Production не участвует.
- Недостаток локальных media-файлов не исправляется подменой рабочего контента.
- Скриншоты не содержат реальные заявки, контакты клиентов или секреты.
- Фиксация результата включает фактическую команду/сценарий и результат.
- Скриншот служит визуальным свидетельством, тесты — свидетельством логики;
  одно не выдаётся за другое.

## 3. Матрица обязательных экранов

Для каждой строки проверяются загрузка, готовое состояние и ошибка; empty state
там, где он возможен. Все экраны используют одну визуальную систему.

| Экран | Desktop | Узкий экран | Клавиатура | Доменные операции |
| --- | --- | --- | --- | --- |
| Вход | Обязательно | Обязательно | Обязательно | Session / ошибки |
| Продукты AI DEF | Обязательно | Обязательно | Обязательно | Поиск, фильтры, переход, reorder |
| Гражданский каталог | Обязательно | Репрезентативно | Обязательно | Свои связи, без final CTA |
| Продукты ARMS | Обязательно | Обязательно | Обязательно | Свой каталог и контекст |
| Редактор AI DEF | Обязательно | Обязательно | Обязательно | Поля, блоки, media, publish |
| Редактор ARMS | Обязательно | Обязательно | Обязательно | Варианты, фото, характеристики |
| Статьи / редактор | Обязательно | Обязательно | Обязательно | Блоки, rich text, автор, рубрика |
| Страницы / редактор | Обязательно | Обязательно | Обязательно | Фиксированные секции, assets |
| Медиатека / picker | Обязательно | Обязательно | Обязательно | Upload, повторный выбор, отмена |
| Сравнение переводов | Обязательно | Обязательно | Обязательно | EN read-only, перевод editable |
| Портал / модули | Обязательно | Репрезентативно | Обязательно | Группы, placements, общий модуль |
| Обращения | Обязательно | Обязательно | Обязательно | Статус, ответственный, заметка |
| Настройки | Обязательно | Обязательно | Обязательно | Пароль и site access |
| История / preview | Обязательно | Обязательно | Обязательно | Версия, восстановление, iframe |

«Репрезентативно» позволяет не дублировать идентичный layout-тест, но не
позволяет пропустить уникальное поведение или полностью игнорировать mobile.

## 4. Сценарии по шагам

### AC-01. Контекст и роли

Дано: тестовые editor, publisher, manager с разными доступами к сайтам.

1. Войти по deep link конкретного материала.
2. Проверить видимость только разрешённых сайтов и разделов.
3. Открыть AI DEF, затем ARMS в отдельной вкладке.
4. Убедиться, что в каждой вкладке свой site, фильтры и язык.
5. Editor не получает доступ к публикации через подстановку URL/API.
6. Пользователь без portal permission не получает портал через прямой маршрут.

Результат: права проверены сервером; заголовок/URL/подтверждения согласованы;
данные другого сайта не мелькают из-за позднего ответа запроса.

### AC-02. Список и возврат

1. Ввести поиск, применить статус и категорию, перейти на следующую страницу.
2. Открыть запись после прокрутки списка.
3. Вернуться стандартной кнопкой редактора и отдельно кнопкой браузера.
4. Сбросить фильтры, проверить полный список.
5. Выполнить запрос без результатов и воспроизвести ошибку загрузки.

Результат: фильтры, страница и позиция сохраняются; пустой результат и
ошибка различаются; кнопки/колонки соответствуют типу сущности. Нет
неработающих чекбоксов, batch actions и сортировки.

### AC-03. Новый неполный материал

1. Создать продукт/статью в тестовом окружении.
2. Ввести часть названия, оставить публикационные поля пустыми.
3. Дождаться autosave, перезагрузить редактор.
4. Открыть другую вкладку формы и вернуться.

Результат: неполный черновик сохранён; сайт не изменился; ввод не потерян;
предупреждения различают draft и требования публикации.

### AC-04. Полнота редактора AI DEF

На тестовом продукте заполнить данные каждого существующего отношения:
images, gallery, features, sub_features, technologies, feature_blocks,
info_blocks, cta_blocks, drone_slider_media и final_cta_block для основного.

1. Переключать разделы и язык; менять только одно поле.
2. Переставить два элемента одной коллекции.
3. Сохранить, перечитать документ и сравнить не тронутые данные.
4. Повторить существенные отличия для гражданского продукта.

Результат: все группы доступны, OneToOne не размножены, независимые массивы
не смешаны, скрытые/неизвестные поля не отброшены.

### AC-05. ARMS с вариантами

1. Создать продукт, заполнить общую информацию и обложку.
2. Добавить два варианта с разными ID/кодами, фотографиями и характеристиками.
3. Изменить порядок вариантов и фотографий.
4. Добавить перевод описания и alt к конкретной фотографии.
5. Удалить один заполненный вариант с подтверждением.
6. Сохранить, перечитать, открыть preview и опубликовать тестовый продукт.

Результат: фотографии/alt не переехали в другой вариант; общий и вариантный
контент разделены; IDs стабильны; до публикации публичные данные не менялись.

### AC-06. Статья и старый контент

1. Открыть материал с текущими blocks и отдельный материал с legacy sections.
2. Вставить текст, список, цитату, изображение и разделитель.
3. Свернуть/развернуть и переставить блоки клавиатурой.
4. Вставить plain text, задать ссылку выделению, вернуться к набору текста.
5. Изменить автора/рубрику через существующий reference flow на тестовых данных.
6. Сохранить и перечитать; открыть preview.

Результат: все типы работают, фокус не прыгает при autosave, неподдержанный
HTML не становится доверенным, legacy не удалён, немедленное действие
общего справочника поясняется до подтверждения.

### AC-07. Страницы

1. Открыть главную AI DEF и страницу документов ARMS.
2. Изменить одну предусмотренную секцию и один допустимый asset.
3. Переключить язык и сохранить его отдельный текст.
4. Проверить неизменность остальных секций и фиксированной структуры.
5. Открыть preview соответствующей страницы/языка.

Результат: нет свободного создания макетов; публичный контракт сохранился;
ограничения carousel действуют; PDF не заменился неподходящим типом файла.

### AC-08. Перевод без потери оригинала

Повторить для ContentNode, ArmsData и PageData.

1. Открыть пустой DE, ничего не менять, вернуться в EN.
2. Убедиться, что один просмотр не записал английские данные в DE.
3. В DE открыть сравнение EN, заполнить одно поле.
4. Сохранить и перечитать оба языка и общие поля.
5. Скопировать оригинал в конкретное пустое поле.
6. Попытаться заменить непустой перевод: требуется явное решение.
7. Проверить вложенный блок/вариант/alt, а не только root description.

Результат: EN read-only, DE отдельно; shared refs/slug/category/порядок не
изменились. Метрика показывает фактическую область, не fallback и не
несуществующее качество перевода. RU есть в ARMS и отсутствует в AI DEF.

### AC-09. Медиатека: список и права

1. Через тестовые загрузки создать изображение, видео и PDF на разных сайтах.
2. Проверить поиск, kind-фильтр, пагинацию и стабильный порядок.
3. Проверить неопределённый размер и недоступный thumbnail.
4. Сделать запрос assets без сессии и с доступом только к другому сайту.

Результат: выдаются файлы своего site; типы различимы; ошибки preview не
роняют каталог. Нет полного сканирования storage и чтения всех файлов при GET.

### AC-10. Picker и legacy media

1. Открыть поле со старым `{path, storage}`.
2. Открыть picker и отменить: старое значение сохранено.
3. Выбрать существующий совместимый asset и применить.
4. В другом материале повторно выбрать тот же asset без upload.
5. Для видео/PDF/image поля проверить недопустимый тип.
6. Подставить asset другого сайта в тестовом API-запросе.
7. Убрать файл из материала, затем восстановить документ из истории.

Результат: поддержаны оба вида refs; чужой asset отклонён сервером;
не удалён физический файл; alt одного использования не меняет другое.

### AC-11. Загрузка и частичная ошибка

1. Выбрать несколько файлов: допустимый, слишком большой, неподходящий формат.
2. Воспроизвести ошибку сети для одного допустимого upload.
3. Повторить только неуспешную загрузку.
4. Во время upload нажать preview/publish/переход в другой раздел.
5. Загрузить файл в picker и отменить вставку.

Результат: видно состояние каждого файла; успешные не дублируются;
не показываются вымышленные проценты; действия ждут upload. Отмена
не подменяет поле, а загруженный asset остаётся в медиатеке с понятным объяснением.

### AC-12. Save, publish и ошибка валидации

1. Изменить опубликованный тестовый материал.
2. Увидеть «Есть изменения» и «Черновик сохранён» как разные состояния.
3. Открыть публикацию и отменить.
4. Вызвать ошибку обязательного поля другого раздела/языка.
5. Перейти по ошибке; проверить раскрытие блока, язык и фокус.
6. Исправить и подтвердить публикацию, включая подготовленные переводы.

Результат: до подтверждения сайт не изменён; после успеха — правильные
badge/время; publish работает с актуальной version, а не устаревшей
версией до flush. Повторный клик не отправляет конкурирующие операции.

### AC-13. Сеть и несохранённая работа

1. Во время набора вызвать ошибку сохранения.
2. Попытаться перейти по меню, сменить сайт, выйти из аккаунта.
3. Выбрать «Остаться», повторить сохранение после восстановления сети.
4. Проверить предупреждение закрытия вкладки и истечение сессии.

Результат: нет ложного saved, очистки текста, бесконечного retry,
непредупреждённого redirect и скрытой записи редакторского контента в localStorage.

### AC-14. Конфликт двух сотрудников

1. Открыть один тестовый материал в двух сессиях.
2. Сохранить изменение в первой.
3. Попытаться сохранить старую version во второй.
4. Использовать разрешённый способ сохранить конфликтную работу.
5. Открыть актуальную версию только после явного подтверждения.
6. Повторить существенную разницу для Page/stash.

Результат: 409 не затёр чужие данные; своя работа сохранена копией/версией
до замены; не реализован обход version/fingerprint. Изменение через
техническую админку также не перезаписывается вслепую.

### AC-15. История и preview

1. Создать несколько версий, открыть историю и ранние версии.
2. Посмотреть историческую версию, закрыть preview.
3. Восстановить выбранную версию в черновик.
4. Проверить, что опубликованная версия не поменялась до publish.
5. Переключить preview desktop/mobile и воспроизвести ошибку загрузки.

Результат: версия/язык/site ясны; нет пустого бесконечного iframe;
возвращаются фокус и место в форме; старые media доступны.

### AC-16. Портал

1. Открыть продукт с группами/негруппированными характеристиками и модулями.
2. Переставить placement в своей группе, снять одно размещение.
3. Проверить, что общий модуль и другие продукты не удалились.
4. Попытаться привязать группу чужого продукта.
5. Проверить выбор preview image и собственный редактор общего модуля.

Результат: прежняя валидация и связи сохранены; данные portal не подменены
публичными Product; нет выдуманного preview для отдельного общего модуля.

### AC-17. Обращения

1. Открыть синтетическую заявку своего сайта.
2. Поменять статус, ответственного и заметку, нажать «Сохранить изменения».
3. Перечитать запись и проверить отсутствие отправленных писем.
4. Повторить конфликт updated_at и уход с несохранённой заметкой.
5. Проверить видимость неизвестного источника для manager и недоступность чужого site.

Результат: редактируемы только workflow-поля; исходное сообщение/контакты
не изменились; заметка не потеряна при ошибке; нет случайного CRM/email flow.

### AC-18. Настройки

Проверять изменения пароля/ролей только на синтетических аккаунтах
изолированного окружения.

Результат: editor/publisher не управляют доступами, manager действует только
на свой site, «Убрать доступ» не удаляет аккаунт. Пароли не сохраняются
в UI после закрытия/успеха и не попадают в URL/log/screenshot.

### AC-19. Доступность

Пройти основные сценарии только клавиатурой: вход → список → редактор →
picker → сравнение → история/preview → возврат. Проверить Tab/Shift+Tab,
Escape, Enter/Space, визуальный фокус, имена controls и status/error announcements.

Результат: нет traps вне диалогов, фокус не уходит под overlay, все действия
без hover доступны, порядок блоков можно менять без drag. Контраст и
labels соответствуют цели AA. Отсутствие отдельной проверки screen reader
указывается честно и не заменяется словами «полностью доступно».

### AC-20. Размеры экрана и изоляция стилей

Проверить минимум 1440×900, 1280×800, 1024×768 и 390×844; при 200% zoom
основные операции остаются доступны. В узком режиме виртуальная клавиатура
не делает форму неотправляемой.

Результат: нет общей горизонтальной прокрутки, обрезанных кнопок и
нечитаемого split; portalled Select/Dialog согласованы с тёмной палитрой CMS;
публичные Header,
contact form и store controls не получили случайную тему CMS.

## 5. Визуальные критерии

- Все рабочие поверхности согласованы с R2, а формы структурированы по R1.
- Список имеет плотность и ясную иерархию R3, но показывает реальные поля AI DEF.
- Карточки media покрывают состояния R4, а не только успешную фотографию.
- Сравнение переводов использует принцип R5 и не обещает review workflow.
- Заголовки/labels/кнопки/иконки одинакового назначения выглядят одинаково.
- Большой sidebar и редактируемый контент не конкурируют по визуальному весу.
- На экране всегда понятно, какое действие основное.
- Нет демонстрационных графиков, декоративных карточек и пустых разделов.
- Ошибки, read-only, fallback и loading оформлены так же аккуратно, как happy path.
- Длинные реальные по форме названия, пустые значения и отсутствующее фото
  не разваливают сетку.

## 6. Производительность и надёжность

- Пагинируются данные, а не только уже загруженный огромный массив.
- Нет загрузки полного storage/всех документов ради одной страницы CMS.
- Тип/дата/размеры media читаются без декодирования файлов на каждый GET.
- Видео в сетке не скачивается целиком и не проигрывается автоматически.
- Изображения вне viewport могут грузиться lazy; место под них зарезервировано.
- Быстрая смена фильтров/сайта не показывает устаревшие ответы.
- Autosave не создаёт параллельных гонок и не блокирует обычный набор текста.
- Новые lazy editor/media imports не ухудшают загрузку публичной витрины.

## 7. Что приложить к сдаче

1. Список изменённых файлов и экранов.
2. Краткое описание новых/изменённых API-контрактов.
3. Результаты разрешённых целевых тестов и build, без пересказа старого отчёта.
4. Скриншоты списка, редактора статьи/продукта, медиатеки, сравнения переводов,
   узкого экрана и хотя бы одного ошибочного состояния на синтетических данных.
5. Для AC-01…AC-20 — «проверено», «не применимо» с причиной или
   «не проверено» с конкретным ограничением. Не подменять выполнением проверки
   чтение исходников там, где нужен реальный сценарий.
6. Отсутствие оставшихся P0/P1. Если они есть, результат не объявляется завершённым.
7. Подтверждение, что рабочие миграции, deployment и реальные данные не затронуты.

Недоступные проверки явно перечисляются. Задание не требует заявлять
«идеальный UI/UX»: требуется показать выполненные критерии и реальные пределы
проверки.
