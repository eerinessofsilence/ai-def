# Порядок реализации и привязка к коду

Этот файл задаёт минимальный технический путь к UI/UX из спецификации.
Он не разрешает запуск команд или миграции сам по себе.

## 1. Подготовка исполнителя

1. Прочитать `AGENTS.md`, текущий diff и файлы из карты ниже.
2. Не считать untracked CMS временным кодом: это действующая база задачи.
3. Посмотреть пять локальных референсов. Не начинать повторный поиск нового
   визуального направления, пока нет конкретного противоречия заданию.
4. Зафиксировать краткий список изменяемых файлов и текущих работающих функций.
5. При разрешённом браузере снять начальное состояние на синтетических данных
   или в режиме чтения. Старые скриншоты и отчёты — только контекст.
6. Выполнять изменения небольшими связными шагами, без удаления существующих
   редакторов до переноса всех полей и операций.

Отдельный дизайн в Figma, новый проект, покупка набора компонентов и развёртывание
стенда на внешнем сервисе не требуются. Разрешённая локальная CMS — основной
артефакт реализации.

## 3. Этапы и условия перехода

### Этап A. Визуальная база и оболочка

Сделать тёмную фирменную систему токенов AI DEF и английский UI, sidebar,
мобильное меню, рабочую шапку,
кнопки, поля, badges, skeleton, ошибки и диалоги. Проверить, что portalled
меню и preview iframe не получили случайные цвета CMS/магазина.

Готовность: вход и навигация по всем существующим разделам используют единый
визуальный язык; длинные названия и touch-экран не ломают layout. На этом
этапе уже не должны исчезать права, маршруты или существующие действия.

### Этап B. Списки

Переработать общий список Products, списки страниц и обращений. Дать точные
названия сущностей и empty states. Сохранить фильтры/пагинацию/возврат,
сделать обновление результатов без демонтажа всей оболочки.

Для существующего reorder выделить последствия немедленного изменения
публичного порядка. Не добавлять неподдержанные сортировки и batch actions.

Готовность: список → отфильтрованный материал → возврат воспроизводит контекст;
ошибки и отсутствие результатов различаются; основные/гражданские продукты,
статьи, портал и модули корректно используют одну основу.

### Этап C. Общий UX редакторов

Согласовать панели, свойства, вкладки, сохранение, публикацию, ошибки,
историю и preview. Начать с одного продукта AI DEF и статьи, затем перенести
паттерн на ARMS и страницы. Вынести только реально повторяющиеся части.

Не переписывать useDocument «заодно». Если новый UI требует изменения хука,
сначала проследить ContentEditor, ArmsEditor, PageEditor и sign-out guard.
Перестановка/удаление блока меняют весь текущий агрегат через существующий
change; компоненты не отправляют конкурирующие независимые записи в тот же
документ.

Готовность: каждый editor сохраняет все текущие поля/связи, поддерживает
неполный draft, реальный preview, публикацию по правам и обработку ошибок.
Ни одно неизвестное/невидимое поле не теряется при сериализации формы.

### Этап D. Переводы

Сделать извлечение переводимых значений в рамках конкретного типа:

- ContentNode: translated-поля из schema + вложенные relations и alt.
- ArmsData: предусмотренные `content` продукта, variants, alt изображений;
  общие name/model_name/code/cover не считать переводом.
- PageData: значения `content` языка в рамках существующей структуры;
  `assets` и идентичность страницы общие.

Возвращать данные для отображения и полноты, не менять источник при чтении.
Операция копирования оригинала отдельная и работает только с нужным полем/
разделом. Не писать универсальный reflection engine, который угадывает
локализованные объекты по любому ключу `en` в произвольном JSON.

Готовность: сравнение и язык работают во всех трёх editor-семействах;
пустой язык не становится заполненным по факту открытия; общие данные и
другие переводы сохраняются. RU доступен только в ARMS.

### Этап E. Минимальная медиатека

Добавить серверный read endpoint для существующих CMS assets и клиентскую
сетку. Затем picker, затем подключить все существующие file-поля и загрузчики.
Прямую загрузку не удалять до сохранения её функциональности в новом flow.

Готовность: один загруженный asset своего сайта можно выбрать повторно без
нового upload; старый текущий файл остаётся видимым; ошибки и отмена выбора
не меняют поле; alt сохраняется в материале, а не глобально.

### Этап F. Остальные экраны и разрешённая приёмка

Завершить портал/модули, обращения, настройки, mobile и все overlay-состояния.
Пройти `04-acceptance.md` в границах разрешения конкретного запуска.
Исправлять обнаруженные дефекты, не начинать бесконечный цикл полировки и
не добавлять новые возможности вне задания.

В завершение записать краткий отчёт о реализации рядом с пакетом или в
существующей документации CMS, явно отделяя новые проверки от исторических.
Не переписывать старый отчёт так, будто его проверки относятся к новой версии.

## 4. Новый контракт: каталог media assets

### 4.1. Endpoint

Добавить `GET /api/cms/<site>/assets/`. Зарегистрировать явный route до
универсального маршрута коллекций. Вызвать существующий `access(request, site)`.
Чужой site, неавторизованный запрос и лишённый права пользователь не должны
получить метаданные чужих файлов.

Параметры:

| Параметр | Значение |
| --- | --- |
| `q` | Подстрока оригинального имени, trim, ограничение длины как у списков |
| `kind` | Пусто / `image` / `video` / `document` |
| `page` | Положительная страница; поведение некорректных значений согласовать с другими списками |

Сортировка: `-created_at`, стабильный вторичный `-pk`. Пагинация по 25.
Данные ограничиваются `MediaAsset.site` до дальнейшей фильтрации. Тип определяется
из нормализованного сохранённого файла и текущего upload-контракта, а не из
непроверенного пользовательского имени. Неподдержанный kind — ясная ошибка
параметра, а не выдача всех файлов по неожиданному условию.

Пример ответа, значения условные:

```json
{
  "items": [
    {
      "ref": {"asset_id": "00000000-0000-0000-0000-000000000001"},
      "name": "product-cover.webp",
      "kind": "image",
      "url": "/media/cms/example.webp",
      "width": 1600,
      "height": 900,
      "size_bytes": null,
      "created_at": "2026-10-23T09:00:00Z"
    }
  ],
  "page": 1,
  "pages": 1,
  "total": 1
}
```

`url` формируется тем же безопасным storage/build_absolute_uri-паттерном,
что используется сейчас; относительный URL в примере условен. Нельзя брать
физический путь или URL из непроверенного query-параметра.

`size_bytes` допустимо `null`: неизвестный размер лучше дополнительного
дорогого запроса к storage для каждой карточки. Не добавлять колонку,
миграцию и backfill только ради отображения размера. Если filesystem/storage
позволяет получить размер дёшево, обработать недоступный файл как неизвестный,
не ломая страницу каталога. Не декодировать изображения повторно при списке.

Не возвращать email загрузившего, внутренние пути storage, заявки и
ненужные персональные сведения. Для этой версии не нужны authors/usage counts.

### 4.2. Что не меняется

`POST uploads/` продолжает возвращать существующие `ref`, `url`, размеры.
Если нужны дополнительные метаданные для новой карточки, расширить ответ
совместимыми полями или перечитать assets после успеха. Не ломать текущих
потребителей upload и не создавать второй upload endpoint.

Для выбора нового файла используется `{asset_id}`. Для старого текущего
использования — прежний `{path, storage}`. Медиатека не разрешает произвольный
legacy path, введённый пользователем. Существующие adapters проверяют
принадлежность asset сайту и допустимость поля и продолжают это делать.

Новый endpoint не добавляет delete, move, rename, copy, import и publish.
Новые миграции не требуются для минимального объёма медиатеки.

### 4.3. Клиентская интеграция

MediaPicker получает минимум необходимых props: site, допустимый тип,
single/multiple, текущие refs и callbacks. Контекст документа и autosave
принадлежит его editor, а не picker. Picker не знает модель Product целиком.

После выбора editor обновляет значение через `change` и карту URL через
существующий `addMedia`. При загрузке использует `trackUpload`; публикация
и уход не опережают upload. Не хранить отдельный несогласованный draft
того же файла в picker и в useDocument после подтверждения.

Search/page в глобальной медиатеке можно хранить в URL; внутренний picker
имеет локальный query и не переписывает параметры открытого редактора.
На смене site запросы и выбор очищаются. Одинаковый asset не добавляется
повторно из-за повторного нажатия «Использовать».

## 5. Изменения schema и представления

Сначала группировать существующие поля на клиенте небольшими явными картами
для типов, где это нужно. Не обрезать payload до видимых полей: обновление
сохраняет остальной `ContentNode.fields` и `sections`.

Если серверная schema не даёт достаточно сведений о применимости file-field,
добавить минимальный атрибут в существующую schema и сохранить совместимость.
Не вычислять допустимость PDF/видео только по расширению случайного старого
URL. Использовать фактическое назначение поля и правила adapter.

Labels UI могут меняться без изменения JSON-ключей, DB-полей и публичных API.
Не добавлять SEO, reviewer, locale_status и publish_at ради расположения
референса. Валидацию не переносить только на клиент.

## 6. Где особенно легко потерять данные

| Место | Опасность | Правило |
| --- | --- | --- |
| Скрытые вкладки | Сериализация только текущих полей | Обновлять часть исходного агрегата, сохранять остальное |
| Переводы | Fallback становится записанным переводом | Чтение и копирование EN — разные операции |
| Варианты ARMS | ID заменяется индексом после перемещения | Стабильные ID и корректные field paths |
| Перестановка блоков | Потеря соседних relations | Менять только целевую коллекцию |
| История | Restore публикует сразу | Восстановить только draft, publish отдельно |
| Legacy media | Отсутствие asset_id объявлено ошибкой | Поддерживать оба MediaRef |
| Media picker | Отмена очищает старое поле | Применять выбор только после подтверждения |
| Reorder | Непонятная немедленная запись в live | Отдельный режим и явное пояснение |
| ReferenceField | Изменение автора принято за draft | Пояснение немедленного общего изменения |
| Session expiry | Redirect демонтирует несохранённую форму | Сохранить форму и показать ошибку доступа |
| Shared module | Удаление placement удаляет модуль | Менять только связь |
| CSS portal | Форма и выпадающий список с несогласованной палитрой | Тематизировать и portalled-контролы |

## 7. Проверки при явном разрешении

Сначала целевые проверки новой логики. Для assets — права/site scope,
поиск/фильтр, стабильная пагинация, несовместимые типы и неизвестные метаданные.
Для переводов — отсутствие мутации при чтении, сохранение EN/общих полей,
вложенные узлы и копирование в непустой перевод. Для сохранения — только
если менялся lifecycle, реальные ошибки/конфликты/очередь.

Не писать тесты, которые сравнивают каждый CSS class с реализацией. UI
проверяется сценариями и несколькими репрезентативными viewport. Тесты
безопасности и данных выполняются на изолированной тестовой БД.

Команды выбираются по реально доступному окружению и package scripts.
Целевой набор: тесты `cms` и затронутых адаптеров; `npm run build` внутри
`frontend`; необходимые проверки diff. Не запускать deployment, сборку
и публикацию Docker-образов ради проверки frontend-редизайна.

Отдельно убедиться, что новая CMS не притягивается в публичный entry,
а общие компоненты не поменяли поведение публичных форм. Если локально
нельзя проверить часть сценариев, отметить её в отчёте без заявления «готово
без ограничений».
