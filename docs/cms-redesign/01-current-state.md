# Текущее состояние и границы изменения

Дата чтения исходников: **23 октября 2026 года**.

Ниже — наблюдения по коду, без запуска приложения, тестов или БД. Это не
визуальный аудит работающей CMS. Исторический отчёт
[`../cms-implementation.md`](../cms-implementation.md) описывает предыдущую
реализацию и её проверки; они не повторялись при подготовке этого задания.

## 1. Существенное отличие от старого описания проекта

В worktree уже существует самостоятельная CMS:

- HTML entry: `frontend/cms/index.html`.
- React entry и маршруты: `frontend/src/cms/main.tsx`.
- Интерфейс и локальные типы: `frontend/src/cms/`.
- API: `backend/cms/`, префикс `/api/cms/`.
- Данные CMS: `WorkspaceAccess`, `Document`, `Revision`, `MediaAsset`, `Page`.
- Публичные доменные модели остаются в `main` и `portal`.
- Техническая админка выделена в `/internal-admin/`; клиентский путь — `/cms/`.

Следовательно, задача — переработать эту CMS. Перенос интерфейса обратно в
Django admin, повторное создание системы черновиков или параллельный frontend
не требуются.

В worktree есть значительные чужие незакоммиченные изменения, включая CMS.
Не очищать дерево, не делать reset/checkout и не заменять каталоги целиком.

## 2. Текущие маршруты

Все пути ниже имеют basename `/cms`.

| Путь | Экран / реализация |
| --- | --- |
| `/login` | Вход, `Login.tsx` |
| `/:site/products` | Каталог AI DEF или ARMS, `Products.tsx` |
| `/ai-def/civil-products` | Гражданский каталог, тот же список |
| `/ai-def/articles` | Статьи, тот же список |
| `/:site/:kind/:id` | `ContentEditor.tsx` или `ArmsEditor.tsx` |
| `/:site/pages` и `/:site/pages/:id` | `Pages.tsx` |
| `/:site/inquiries` и `/:site/inquiries/:id` | `Inquiries.tsx` |
| `/ai-def/portal` и `/ai-def/modules` | Каталог портала и общие модули |
| `/:site/settings` | Пароль и доступы, `Settings.tsx` |
| `/:site/preview/:id/:lng` | Защищённый preview, `Preview.tsx` |

Сайты: `ai-def` и `arms`. ARMS не имеет раздела статей и клиентского портала.
Нельзя определять site по случайному frontend hostname: он есть в URL и
проверяется сервером. `id` может быть UUID документа или `live-<target_id>`.
Открытие live-записи создаёт/находит её редакторский документ через существующий
контракт. Старые ссылки должны продолжить работать.

## 3. Что уже есть и должно сохраниться

### Списки

Поиск, фильтры состояния/категории, серверная пагинация по 25 элементов,
сохранение фильтров через query string, возврат из редактора через `from`,
сохранение scroll списка продуктов в sessionStorage. Существующие состояния:
`draft`, `published`, `changes`.

Перестановка продуктов — отдельный режим. POST `reorder/` сразу меняет порядок
на сайте. Это не отложенное изменение документа. Новые неопубликованные записи
не имеют `target_id` и не перемещаются тем же контрактом.

### Материал и сохранение

`use-document.ts` управляет загрузкой, autosave после 1200 мс покоя,
очередью сохранения, отслеживанием upload, ошибками полей, конфликтом 409,
блокировкой ухода и сохранением перед logout. `Document.version` и fingerprint
защищают от параллельных изменений и изменений через техническую админку.

В редакторах есть preview, история с постраничной загрузкой ранних версий,
публикация, восстановление, копирование или сохранение конфликтной работы.
Набор допустимых действий зависит от типа материала. У страниц нет свободного
создания, дублирования или снятия с публикации. Для общих модулей нет отдельного
публичного preview.

### AI DEF: продукты и статьи

`ContentEditor.tsx` получает schema, `ContentFields.tsx` рисует поля и связи.
`ContentAdapter` на сервере явно описывает агрегаты:

- Основной и гражданский продукты: фотографии, галерея, features,
  sub-features, технологии, feature/info/CTA-блоки, media карточки на главной.
- Только основной продукт: завершающий CTA OneToOne.
- Статья: основные поля, hero image, hero images, blocks и legacy sections.
- Портал: изображения, галерея, презентация, группы характеристик,
  характеристики, группы модулей, placements, текстовые блоки.
- Общий модуль: собственные изображения и характеристики.

Справочники категорий, авторов и рубрик доступны через `references/`.
Изменение существующего справочника применяется сразу ко всем связанным
материалам. PUT требует права публикации и fingerprint версии записи.

### ARMS

`ArmsEditor.tsx` редактирует единый агрегат: общие name/slug/brand/category,
cover, переводы описания и характеристик, variants с кодом, названием,
переводами, фотографиями и alt. Общие характеристики и характеристики
варианта — разные массивы, порядок фотографий значим.

### Страницы

`Pages.tsx` редактирует предусмотренные секции фиксированных макетов,
`PageAdapter` сохраняет содержимое и assets. Публичный frontend использует
`PageContentProvider`.

AI DEF: главная, о компании, технологии, решения, поддержка. ARMS: поддержка,
разрешения и сертификаты. Структура определяется текущими page payloads,
а не свободным набором виджетов. На главной блок каталога имеет ограниченный
набор редактируемых текстов. Общие файлы не размножаются по языкам.

### Переводы

Интерфейс CMS на русском. Контент AI DEF — EN/DE/SK/ES/FR/IT; ARMS дополнительно
RU. Modeltranslation и image translations на сервере остаются разными
механизмами. В CMS есть fallback-пояснения и явное копирование английского
текста; параллельного редактора сравнения пока нет.

Не считать заполненным перевод, который только отображается через fallback.
У страниц текущий frontend может показывать английский объект вместо пустого
перевода; при переработке это нужно выразить явно, сохраняя правила adapter.

### Файлы

`MediaRef` — либо `{asset_id}`, либо прежний `{path, storage}`. `mediaURL`
разрешает ссылки через карту `media` ответа. Файлы уже загружаются через
`POST /api/cms/:site/uploads/` и хранятся в `MediaAsset`.

Изображения: до 20 МиБ; сервер декодирует/обрабатывает изображение и сохраняет
нормализованный файл. Видео MP4/WebM — до 45 МиБ. PDF — до 20 МиБ. Входные
ограничения и допустимый тип зависят от конкретного поля; серверная проверка
приоритетна. Нельзя обещать поддержку SVG в upload только потому, что в
старой модели могла использоваться SVG-иконка.

Сейчас нет самостоятельной медиатеки, API пагинированного каталога файлов,
выбора ранее загруженного asset, folder-модели, серверных usage counts,
глобального alt и гарантированно доступных thumbnail для всех типов.

### Обращения

Список фильтруется по сайту и статусу; есть «Назначенные мне». Неопределённые
старые источники доступны управляющему отдельно. Изменяются только status,
assigned_to, internal_note; конфликт проверяется через updated_at.
Сохранение явное. Работа с обращением не отправляет письмо клиенту.

### Доступы

`session.tsx` использует session auth, `api.ts` — same-origin credentials и
CSRF. Это отдельный контур от token auth клиентского портала.

| Роль | Действия |
| --- | --- |
| `editor` | Просмотр разрешённого сайта, работа с черновиками и обращениями |
| `publisher` | Предыдущее + публикация, снятие, изменение общих справочников, порядка |
| `manager` | Предыдущее + управление доступами сайта и неопределёнными обращениями |

Портал дополнительно требует `portal.change_portalproduct` либо superuser.
Сервер — источник прав; скрытая кнопка не заменяет серверную проверку.

## 4. Основания для переработки, видимые в коде

Это точки приложения задания, а не результаты пользовательского теста:

1. `cms.css` задаёт тёмную основу `#172b4a`, светлые тексты и собственные
   многочисленные состояния. Целевая рабочая тема должна стать светлой.
2. Список один для нескольких сущностей: встречаются общие подписи «Продукт»
   и пустые состояния про продукт даже для других типов. Нужна точная лексика.
3. Главные панели, боковые разделы, язык, свойства и служебные действия
   распределены по трём редакторам разными способами. Нужен общий UX-контракт.
4. Поля формируются в основном по schema. Рабочие группы и полезные summary
   нужно добавить в представлении, сохранив полный набор полей и данных.
5. Редактирование переводов сводится к переключателю языка. Нужны обзор
   заполненности и сравнение с оригиналом.
6. Upload доступен внутри полей; повторный выбор файла требует медиатеки.
7. Rich text использует `contentEditable` и `execCommand`, paste — plain text.
   Изменение toolbar не должно разрушить выделение и фокус.
8. `CMSImage` уже умеет показывать ошибку, но другие места используют обычный
   `img`. Состояния недоступного медиа должны быть последовательными.
9. Есть Select и Collapsible проекта. CMS использует элементы общей витрины;
   новая палитра должна быть ограничена CMS, включая portalled-панели.

## 5. Инварианты вне визуального задания

- Публичные API, slug, SEO URL, порядок выдачи и языковые URL сохраняются.
- Продукт портала не превращается в публичный Product и наоборот.
- Placement остаётся связью продукта с общим модулем и его порядком.
- Наследованные разделы статьи не удаляются и не конвертируются молча.
- Черновик, asset upload и публикация — разные действия.
- Сохранение черновика не публикует его; restore не публикует автоматически.
- Публикация включает материал и его подготовленные языки по текущему adapter.
- Конфликт не решается принудительным overwrite.
- Физические файлы и рабочие записи не удаляются в рамках редизайна.
- Существующая семантика contact/email и права технической админки сохраняются.
- Новые поля данных, миграции и фоновые сервисы не вводятся ради макета.
